# دسترسی و گروه `argus`

> **این صفحه برای کیست؟** برای مدیر سیستمی که ARGUS را نصب می‌کند، و برای سرپرست
> تیم SOC که می‌خواهد تحلیلگرانش بدون این‌که تمام روز `sudo` بزنند کار کنند.

ARGUS ثبت می‌کند که روی یک میزبان چه اتفاقی می‌افتد. آن داده «شاهد» است، پس
به‌صورت پیش‌فرض **فقط برای root** قابل خواندن است: دیمن با root اجرا می‌شود، سپر
کرنل فقط به root پاسخ می‌دهد، و رویدادهای ذخیره‌شده تنها برای root خواندنی‌اند.
این صفحه توضیح می‌دهد *چرا* این پیش‌فرض انتخاب شده، و چطور می‌توانید با افزودن
تحلیلگران به یک گروه، دقیقاً همان اندازه دسترسی که لازم دارند را بدهید — نه
بیشتر.

---

## چرا همه‌چیز به‌صورت پیش‌فرض فقط برای root است؟

سه ویژگی ARGUS باعث می‌شود root مالک طبیعی پیش‌فرض باشد:

۱. **دیمن و سپر.** سپر یک ماژول کرنل است که اجازه نمی‌دهد بارش برداشته شود یا
   فرآیندهای محافظت‌شده‌اش کشته شوند. دیمن خود را به آن ثبت می‌کند. هر دو ذاتاً
   سطح‌بالا (privileged) هستند.
۲. **داده، شاهد است.** پرونده‌های رویداد، زنجیرهٔ هش، و مجوز، زیر پوشه‌هایی با
   مجوز `0750` و مالکیت `root:argus` قرار دارند. کاربری که عضو گروه `argus`
   نیست، اصلاً نمی‌تواند آن‌ها را بخواند.
۳. **کم‌ترین اختیار.** بیشتر فرمان‌های ARGUS یا وضعیت را تغییر می‌دهند (روشن/خاموش
   کردن سپر، ویرایش پیکربندی، آزادسازی رمز) یا دادهٔ خام شاهد را بیرون می‌دهند.
   پیش‌فرضِ root، همان پیش‌فرضِ امن و بی‌صدا است.

هزینهٔ این پیش‌فرض روشن است: هر خواندن به `sudo` نیاز دارد، که برای تحلیلگر کند و
در تیکت‌ها پرصدا است. گروه `argus` این هزینه را برای کارهای فقط-خواندنی حذف
می‌کند، بدون این‌که سمت نوشتن ضعیف شود.

---

## گروه `argus`

نصب‌کننده یک گروه سیستمی به نام **`argus`** می‌سازد و دسترسی خواندن به دادهٔ ARGUS
را به آن می‌دهد، در حالی که بخش‌های حساس را فقط برای root نگه می‌دارد. نتیجه یک
تقسیم‌بندی تمیز است:

| | عضو گروه `argus` | کاربر بیرون گروه |
|---|---|---|
| خواندن رویدادها، جست‌وجو، شمارش | **بله** | نه |
| تأیید زنجیره (`argus-cli verify`) | **بله** | نه |
| خروجی/فوروارد به SIEM | **بله** | نه |
| خواندن لاگ رمزنگاری‌شده (رمزگشایی) | **بله** | نه |
| تغییر پیکربندی (mode، نگهداشت، فوروارد) | نه — نیاز به root | نه |
| آزادسازی رمز سپر | نه — نیاز به root | نه |
| برداشتن سپر | نه — نیاز به root | نه |

به‌طور خلاصه: **خواندن واگذار می‌شود، تغییر نه.** تحلیلگر آزادانه بررسی می‌کند؛
فقط تعداد کوچکی از کارهای سطح‌بالا هنوز به root نیاز دارند.

> **توجه.** مکان دقیق انبار رویداد روی دیسک، عمداً در این مستندات منتشر نشده است.
> این یک جزئیات داخلی است و مستند نکردنش بخشی از روشی است که ARGUS با آن از شاهد
> محافظت می‌کند. از فرمان‌های `argus-cli` در ادامه استفاده کنید — آن‌ها رابط
> پشتیبانی‌شده‌اند و همیشه انبار را برایتان پیدا می‌کنند.

---

## افزودن یک تحلیلگر به گروه

یک فرمان، یک‌بار برای هر کاربر، با root:

```bash
sudo usermod -aG argus <username>
```

کاربر باید **خارج و دوباره وارد** شود (یا یک نشست تازه باز کند) تا عضویت جدید
گروه اثر کند — عضویت گروه هنگام باز شدن نشست تعیین می‌شود.

تأیید کنید که کار کرده:

```bash
id <username>          # خروجی باید شامل "argus" باشد
```

از آن نشست به بعد، فرمان‌های فقط-خواندنی **بدون `sudo`** کار می‌کنند:

```bash
argus-cli status
argus-cli list --last 50
argus-cli verify
argus-cli count
argus-cli export --format json --from 10/01/2026
```

اگر فرمانی هنوز root می‌خواهد، یعنی نشست هنوز گروه را برنداشته است — خارج و
دوباره وارد شوید، یا برای تازه‌سازی همین پوسته `newgrp argus` را اجرا کنید.

---

## برداشتن دسترسی

کاربر را دقیقاً همان‌طور که اضافه کردید، حذف کنید:

```bash
sudo gpasswd -d <username> argus
```

نشست بعدی او به‌سادگی گروه را نخواهد داشت و فرمان‌های خواندن دوباره رد می‌شوند.
هیچ چیز دیگری تغییر نمی‌کند؛ شاهد دست‌نخورده می‌ماند.

---

## این چطور به SOC کمک می‌کند؟

یک SOC خوش‌اداره از یک عاملِ اندپوینت سه چیز می‌خواهد: دسترسی سریع به داده، یک
خط روشن دور چیزهایی که تغییرپذیرند، و یک ردِ حسابرسی. گروه `argus` هر سه را
می‌دهد:

* **بدون مالیاتِ `sudo` روی بررسی‌ها.** دسته‌بندی (triage)، جست‌وجو، و تأیید
  زنجیره، بخش عمدهٔ روز یک تحلیلگر است. انجام آن‌ها بدون بالا بردن سطح دسترسی،
  گردش کار را سریع نگه می‌دارد و لاگ `sudo` را معنادار نگه می‌دارد — وقتی *واقعاً*
  استفاده شود، یعنی کار سطح‌بالایی رخ داده است.
* **جداسازی تمیز وظایف.** تحلیلگران می‌خوانند؛ مدیران تغییر می‌دهند. یک حساب
  تحلیلگرِ آلوده نمی‌تواند عامل را بازپیکربندی کند، یک مقصد را خاموش کند، یا سپر
  را آزاد کند.
* **شاهد به‌صورت پیش‌فرض محرمانه می‌ماند.** چون خواندن به گروه گره خورده و نه
  برای همه‌جهان، دادهٔ رویداد هرگز برای حساب‌های بی‌ربط روی میزبان افشا نمی‌شود.

یک الگوی رایج این است که گروه را بخشی از ایمیج استاندارد SOC کنید، تا تحلیلگر
تازه‌وارد همان لحظه‌ای که حسابش ساخته می‌شود، مولد باشد:

```bash
# روی اندپوینت، یک‌بار برای هر تحلیلگر
sudo usermod -aG argus "$SOC_USER"
```

## نکته‌ای دربارهٔ CLI و `sudo`

چند فرمان **همیشه** سطح‌بالا هستند و اگر بدون root اجرا شوند، خودشان این را
می‌گویند — مثلاً `argus-cli mode`، `argus-cli retention`، `argus-cli forward`،
`argus-cli release` و `argus-cli remove`. این عمدی است: آن‌ها وضعیت امنیتی میزبان
را تغییر می‌دهند، نه فقط آن‌چه را که می‌بینید.

اگر یک فرمانِ خواندن بگوید لاگ فقط برای root است، تقریباً قطعاً آن را به‌عنوان
کاربری اجرا می‌کنید که **عضو گروه `argus` نیست**. کاربر را اضافه کنید (بالا) یا
همان یک فرمان را با `sudo` اجرا کنید — پیام عمداً صریح است تا این دو حالت هرگز
یکسان به نظر نرسند.

---

## خلاصه

* ARGUS به‌صورت پیش‌فرض فقط برای root است، چون شاهد تولید می‌کند و یک سپر کرنل را
  کنترل می‌کند.
* گروه `argus` دسترسی **فقط-خواندنی** به آن شاهد می‌دهد، بدون `sudo`، برای
  تحلیلگرانی که به آن نیاز دارند.
* افزودن با `usermod -aG argus <user>`؛ حذف با `gpasswd -d <user> argus`.
* کارهای سطح‌بالا سطح‌بالا می‌مانند — خواندن واگذار می‌شود، تغییر نه.
* مکان دقیق انبار عمداً مستند نشده است؛ از `argus-cli` استفاده کنید.
