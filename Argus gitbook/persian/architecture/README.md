# معماری

ARGUS سه لایه دارد، با مرزی روشن بین «کرنل» و «فضای کاربر». تمام منطق در فضای کاربر
است؛ در کرنل فقط یک حسگر eBPF و یک ماژول سپر کوچک اجرا می‌شود.

```
┌─────────────────────────────────────────────────────────────┐
│ فضای کاربر                                                  │
│                                                             │
│  capture engine           ← مغز: خواندن ring buffer،        │
│  (دیمن)                      بلاکچین، ذخیره، هشدار، anchor   │
│                                                             │
│  resolver                 ← نگاشت PID → IP                  │
│                                                             │
│  argus-cli                ← اپراتور: status/verify/list/…   │
├─────────────────────────────────────────────────────────────┤
│ مرز کرنل                                                    │
├─────────────────────────────────────────────────────────────┤
│ حسگر eBPF                 ← ۲۱ هوک، ring buffer             │
│ ماژول سپر                 ← ۴ kprobe، ضد دست‌کاری           │
└─────────────────────────────────────────────────────────────┘
```

---

## چرا این تقسیم‌بندی؟

هر خط کدی که در کرنل اجرا می‌شود، سطح حملهٔ کرنل است. ARGUS تا حد امکان منطق را از کرنل
بیرون کشیده:

- **حسگر eBPF** رویداد خام می‌فرستد و هیچ تصمیمی نمی‌گیرد. مزیت: verifier کرنل آن را
  *قبل از اجرا* اثبات می‌کند، پس خطای حافظه در آن ممکن نیست.
- **سپر** تنها ماژول کرنل دست‌نویس است و کارش فقط «محافظت از جان دیمن» است.
- **دیمن** تمام منطق را دارد و اگر کرش کند، کرنل سالم می‌ماند.

---

## مقایسه با معماری نسل قبل (v14)

| | v14 | v15 |
|---|---|---|
| حسگر | ~۲۴ kprobe دست‌نویس در ماژول کرنل | یک برنامهٔ eBPF (تأییدشده توسط verifier) |
| کد کرنل سفارشی | یک ماژول بزرگ | ماژول سپر کوچک + برنامهٔ eBPF |
| منطق (بلاکچین، ذخیره، هشدار) | مخلوط در کرنل | کامل در فضای کاربر |
